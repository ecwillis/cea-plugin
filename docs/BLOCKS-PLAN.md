# Theme Blocks: Implementation Plan

Adds a block framework to CEA Plugin so admin-editable content (starting with
forms) can be dropped into a live theme from **either** the Gutenberg editor
or Elementor, from one shared PHP rendering core.

Decisions locked in with the user (2026-08-22):

- **Scope**: build a small reusable block registry, not a single one-off
  block. First real block is the existing form builder ("CEA Form").
- **Elementor**: soft dependency. Widgets register only when Elementor is
  active (`elementor/loaded`); the plugin works fully without it.
- **Build tooling**: introduce `@wordpress/scripts` (first Node/npm build
  step in this plugin). JSX + `block.json`, built with `wp-scripts build`.
- **Capability**: anyone who can edit posts/pages (`edit_posts`) can insert
  the block/widget — same as core Gutenberg blocks. This is narrower than
  `CEA_Forms::register_post_type()`, which gates the **form builder itself**
  behind `manage_options`; placing an already-published form on a page is a
  separate, lighter permission.

## 1. Core architectural insight

Forms already render through one function:
[CEA_Form_Renderer::render_shortcode()](../includes/forms/class-cea-form-renderer.php).
The shortcode, the Gutenberg block's `render_callback`, and the Elementor
widget's `render()` should all call **the same function**. That single
decision is what makes Gutenberg/Elementor "interoperable" here — there is
one source of truth for markup, sanitization, and asset enqueuing
(`CEA_Forms::enqueue_public_assets()` already fires from inside the render
path, so both editors get correct front-end CSS/JS for free, no separate
wiring needed).

Everything else in this plan exists to get form data (which form was
selected) into that one function from two different editor UIs.

## 3. Shared data layer (`CEA_Form_Picker`)

New small class, used by *both* editors so the list of "choosable forms" and
its permission rule live in exactly one place:

```php
class CEA_Form_Picker {
    // Published forms only, id + title, no fields/actions/secrets.
    public static function get_choices(): array { ... }
}
```

- Backed by `get_posts()` against `CEA_Forms::POST_TYPE` filtered to
  `post_status = publish`.
- No new capability is invented: reading this list requires `edit_posts`,
  matching the "who can place blocks" decision. It intentionally does **not**
  require `manage_options`, even though editing a form's fields/actions
  still does.

## 4. REST endpoint for the Gutenberg picker

`includes/blocks/class-cea-rest-form-picker-controller.php`:

- Route: `GET /wp-json/cea/v1/forms`
- `permission_callback`: `current_user_can( 'edit_posts' )`
- Returns `CEA_Form_Picker::get_choices()` as `[{id, title}]`
- This is intentionally a *new*, narrow route rather than exposing the
  `cea_form` CPT over REST wholesale — the CPT's own capabilities are all
  `manage_options` (see `class-cea-forms.php`), and widening those to make
  the built-in posts REST controller usable by editors would leak the form
  *builder* (fields/actions config) to non-admins. The narrow controller
  avoids touching that capability model at all.

Elementor's widget doesn't need this REST route — its control options are
built server-side in PHP directly from `CEA_Form_Picker::get_choices()`
inside the admin request, same as any other Elementor `SELECT2` control.

## 5. Block registry (extensibility for future block types)

`class-cea-block-registry.php` holds an array of block definitions and
drives both registrations from one place, so a second block later (e.g. a
future "CEA Testimonial" block) is one new definition file, not new
bootstrap code:

```php
class CEA_Block_Registry {
    private static array $blocks = [];

    public static function register( CEA_Block_Base $block ) {
        self::$blocks[ $block->slug() ] = $block;
    }

    public static function init_gutenberg() {
        foreach ( self::$blocks as $block ) {
            register_block_type( $block->build_path(), [
                'render_callback' => [ $block, 'render' ],
            ] );
        }
    }

    public static function init_elementor( $widgets_manager ) {
        foreach ( self::$blocks as $block ) {
            if ( $block->elementor_widget_class() ) {
                $widgets_manager->register( new ( $block->elementor_widget_class() )() );
            }
        }
    }
}
```

`CEA_Block_Base` defines the shared contract each block type implements:
`slug()`, `build_path()`, `render( $attributes )`, `elementor_widget_class()`
(nullable), and an attribute-normalization method so the same
validation/fallback logic (e.g. "form not found or unpublished") is used
regardless of which editor produced the attributes.

## 6. Gutenberg: the CEA Form block

`src/blocks/form/block.json`:

```json
{
  "apiVersion": 3,
  "name": "cea/form",
  "title": "CEA Form",
  "category": "cea",
  "icon": "email-alt",
  "attributes": { "formId": { "type": "number", "default": 0 } },
  "supports": { "html": false },
  "editorScript": "file:./index.js"
}
```

- **Dynamic block**: `save()` returns `null`; all markup comes from PHP via
  `render_callback`, matching how the shortcode already behaves and avoiding
  any duplicated markup/serialization drift.
- **Editor UI** (`edit.js`, JSX): a `SelectControl` in `InspectorControls`
  populated from `GET cea/v1/forms` (via `@wordpress/api-fetch`, reusing the
  REST nonce Gutenberg already wires up), plus `<ServerSideRender block="cea/form" attributes={...} />` in the canvas so the editor preview *is* the real
  PHP output — no second render implementation in JS.
- **Empty/error states**: "Select a form" when `formId` is 0; "This form is
  not published" if the picked form was unpublished/deleted after insertion
  (checked in PHP `render()`, not just at insert time).
- PHP side (`class-cea-form-block.php`) registers a custom `cea` block
  category via the `block_categories_all` filter and calls
  `CEA_Block_Registry::register()` on `init`.

## 7. Elementor: the CEA Form widget

Loaded conditionally — nothing in this file executes unless Elementor is
active:

```php
add_action( 'elementor/loaded', function () {
    require_once __DIR__ . '/includes/integrations/class-cea-elementor-integration.php';
    CEA_Elementor_Integration::register_hooks();
} );
```

`CEA_Elementor_Integration`:
- Hooks `elementor/elements/categories_registered` to add a "CEA Plugin"
  widget category (mirrors the Gutenberg `cea` category).
- Hooks `elementor/widgets/register` and calls
  `CEA_Block_Registry::init_elementor( $widgets_manager )`.

`class-cea-form-elementor-widget.php` extends `\Elementor\Widget_Base`:
- `get_name()` / `get_title()` / `get_icon()` / `get_categories()` boilerplate.
- One control: `form_id` as `SELECT2`, `options` built from
  `CEA_Form_Picker::get_choices()`.
- `render()` calls the **same** `CEA_Form_Block::render( [ 'formId' => $this->get_settings('form_id') ] )` used by the Gutenberg side (which itself
  calls `CEA_Form_Renderer::render_shortcode()`), so front-end markup, CSS
  classes, and asset enqueuing are identical between builders.
- Elementor's own editor preview is a real front-end render (Elementor
  renders widgets via ajax/iframe against the live site), so the "preview
  matches production" property holds here too without extra work.

## 8. Attribute parity

| Concern                  | Gutenberg                    | Elementor                     |
|---------------------------|-------------------------------|--------------------------------|
| Form selection            | `attributes.formId` (number)  | `form_id` SELECT2 control      |
| Data source for picker    | REST `cea/v1/forms`           | `CEA_Form_Picker::get_choices()` (direct PHP call) |
| Render                    | `render_callback` → `CEA_Form_Block::render()` | `render()` → same `CEA_Form_Block::render()` |
| Validation/fallback       | `CEA_Block_Base::normalize_attributes()` (shared) | same |

Normalizing both into the same `[ 'formId' => int ]` shape before calling
`render()` is what keeps this a one-function render core instead of two
parallel implementations that can drift.

## 9. Build tooling changes

- Add `package.json` with `@wordpress/scripts` as the only devDependency to
  start; scripts:
  - `"build": "wp-scripts build"`
  - `"start": "wp-scripts start"`
  - `"lint:js": "wp-scripts lint-js"`
  - `"lint:css": "wp-scripts lint-style"`
- `@wordpress/scripts` auto-discovers `src/**/block.json` and produces one
  entry per block plus an `index.asset.php` (dependency + version array) —
  no manual webpack config needed even as more blocks are added later.
- PHP registers built blocks with
  `register_block_type( CEA_PLUGIN_DIR . 'build/blocks/form' )`, reading the
  generated `index.asset.php` for script dependencies/versioning
  automatically (handled by `register_block_type()` itself).
- `build/` is committed to `.gitignore`; CI/deploy runs `npm ci && npm run
  build` before packaging the plugin zip. **Note this in README** as a new
  step, since none of the plugin's current assets require a build.
- **Version floor**: `register_block_type()` accepting a directory path (and
  reading `block.json`) requires WP 5.8+; `ServerSideRender` from
  `@wordpress/server-side-render` and modern `block.json` `apiVersion: 3`
  are safe from 6.0+. The plugin header currently declares `Requires at
  least: 5.7`. Recommend bumping that to `6.3` as part of this work — 5.7
  is past its own support window and blocking on it buys nothing here. This
  only affects the plugin header/readme, not a new question — flagging it
  as a call I'm making rather than leaving unresolved.

## 10. Security / permissions checklist

- REST controller: `permission_callback` on `edit_posts`, matches the
  "who can place blocks" decision; never exposes field/action config.
- `render()` (both editors) re-validates the form is still `publish`ed at
  render time — an editor could insert a block for a form an admin later
  unpublishes; render should degrade gracefully (empty/notice), not fatal.
- No new public-facing attack surface: front-end output still goes through
  `CEA_Form_Renderer::render_shortcode()`, which already owns nonce/
  honeypot/rate-limit/sanitization for the form itself. The block/widget
  layer only ever supplies a form ID, never freeform HTML.
- Elementor widget controls are admin-only (rendered inside wp-admin), same
  trust boundary as the existing CEA admin screens.

  - `rest_get_server()->get_routes()` contains `/cea/v1/forms`

    registered under the `cea` category.
- Manual QA checklist (add to README): insert the block in Gutenberg as an
  Administrator and as an Editor-role user; confirm the picker only lists
  published forms; confirm front-end output matches the `[cea_form]`
  shortcode's existing output byte-for-byte; repeat with Elementor once
  installed for testing; confirm full-page caching guidance in the existing
  README section still applies (dynamic render, not cached HTML).

## 12. Suggested implementation order

1. ✅ **Done** — `package.json` + `@wordpress/scripts` scaffold, empty
   `cea/form` block that just renders a placeholder. Confirmed the build
   pipeline end to end: `npm install`, `npm run build` (auto-discovers
   `src/blocks/form/block.json`, zero webpack config needed), and
   `CEA_Blocks::register_blocks()` wired into `CEA_Plugin::init()`,
   registering from `build/blocks/form` and no-op'ing safely (no fatal) if
   `build/` doesn't exist yet on an unbuilt checkout — verified directly.
   Two environment snags worth remembering for later phases:
   - `typescript` had no explicit version pinned anywhere in the tree, so
     npm resolved a brand-new `typescript@7.x` that crashes
     `@typescript-eslint`'s `ts-api-utils@1.4.3` (bundled by
     `@wordpress/eslint-plugin` 22.x) at load time. Fixed by pinning
     `"typescript": "5.6.3"` as a direct devDependency so it dedupes
     everywhere.
   - `wp-scripts lint-js` / `lint-style` with no args sweep the *entire*
     project by default, including the plugin's pre-existing hand-written
     `assets/*.js`, `assets/*.css`, and `tests/*.js`, which predate this
     tooling and don't conform to it. Scoped both npm scripts to `src/`
     (`lint:css` needed the glob placed *before* `--allow-empty-input` —
     `minimist`, which wp-scripts uses internally to detect "was a file arg
     passed", otherwise swallows the glob as that flag's value and falls
     back to scanning everything).
   - Bumped `Requires at least` to 6.3 per §9, since
     `register_block_type()` with a directory path needs 5.8+ and 5.7 is
     past its own support window.

   `npm run lint:js`, `npm run lint:css`, `php -l` across the plugin, and
   the existing `tests/forms-js-smoke.js` / `forms-admin-js-smoke.js` all
   pass with these changes in place.

2. `CEA_Form_Picker` + REST controller.
3. `CEA_Block_Base` / `CEA_Block_Registry` skeleton.
4. Gutenberg `CEA_Form_Block`: real `render_callback`, `edit.js` with
   `SelectControl` + `ServerSideRender`.
5. `CEA_Elementor_Integration` + `CEA_Form_Elementor_Widget`, gated on
